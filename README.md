## The Problem: Why Invariants is Needed

Autonomous AI coding agents (Claude, Cursor, Copilot, Antigravity) are massive productivity multipliers. However, they share a critical fundamental vulnerability:

### The Symmetry Flaw of Traditional Linters
In conventional toolchains (ESLint, SwiftLint, Biome, Flake8), **the AI agent and the linter rules share the exact same permissions**. 
When an AI agent is refactoring a large codebase and encounters a linting failure:
1. It adds `// swiftlint:disable` or `// eslint-disable-next-line`.
2. It edits `.swiftlint.yml` to disable the rule or widen exclusions.
3. It bypasses git hooks with `git commit --no-verify`.
4. It deletes or modifies the test that failed.

The agent optimizes for making the build pass and completing the task—not for preserving long-term architectural contracts. This leads to **silent architectural erosion and codebase degradation**.

### The Solution: Cryptographic Trust Asymmetry
`invariants` introduces a strict trust boundary:
- **The AI Agent has Code Authority**: It can write application code, run tests, and propose implementations at high velocity.
- **Only the Human has Architectural Authority**: The rules, their SHA-256 tree fingerprints, the team signers, the protected trunk branch, and the version floor are sealed inside `invariants/registry.lock.sig`.
- **The Biometric Air Gap**: An agent cannot weaken a rule, authorize a key, or rewrite history without an Ed25519 cryptographic signature generated by your **physical Touch ID on the Apple Secure Enclave**.

## Core Pillars

### 1. True Semantic AST Inspection vs. Surface Linters
Traditional linters rely primarily on regex matching or shallow token checks for generic style conventions (indentation, line length, `no-force-try`). They cannot enforce high-level architectural contracts.

`invariants` provides **`InvariantKit`** (powered by `SwiftSyntax`, `IndexStoreDB`, and TypeScript AST parsers), allowing you to author custom rules that query real language symbols, types, and call hierarchies:
- **Clean Architecture & Layer Isolation**: Presentation layer components (UI views, view models, controllers) must never import raw database drivers or call network clients directly; all data access must pass through a repository or service protocol.
- **Type-Safe API Contracts**: Network requests must never use raw string literals for URL endpoints; all routes must use strongly-typed route definitions (e.g. `APIEndpoint.Users.profile`).
- **Design System Token Enforcement**: No hardcoded hex color literals (`#3B82F6`) or magic layout numbers in UI components; all styling must use typed design system tokens (`Theme.Color.primary`, `Theme.Spacing.md`).
- **Security & PII Protection**: Never pass raw user tokens, passwords, or PII into logger or `print(...)` statements; all logged objects must conform to a `SanitizedLoggable` contract.
- **Domain Boundary & DTO Isolation**: Internal database entities (ORM models) must never be returned directly in public API responses without an explicit DTO / View Model mapping.

#### Example: Enforcing Type-Safe API Endpoints (Swift)
```swift
// invariants/rules/forbid-raw-endpoint-strings/rule.swift
import InvariantKit

@main
struct ForbidRawEndpointStringsRule: SwiftRule {
    func check(_ ctx: RuleContext) throws(RuleError) -> [Violation] {
        return ctx.swift.files
            .calls(named: "request", "fetch", "get", "post")
            .whereFirstArgument(is: .stringLiteral)
            .violations(
                code: "RAW-ENDPOINT-STRING",
                message: { "\($0.callee) called with raw string literal: \($0.firstArgumentStringValue ?? "")" },
                fix: "Use strongly-typed APIEndpoint route enum instead of raw string"
            )
    }
}
```

#### Example: Presentation Layer Isolation (TypeScript)
```typescript
// invariants/rules/isolate-presentation-layer/rule.ts
import { defineRule, Violation } from "@invariants/kit";
import * as ts from "typescript";

export default defineRule({
  check(ctx) {
    const violations: Violation[] = [];

    for (const filePath of ctx.files) {
      // Scope to presentation / UI layer
      if (!filePath.includes("/ui/") && !filePath.includes("/components/")) continue;

      const sourceFile = ctx.sourceFile(filePath) as ts.SourceFile;
      ts.forEachChild(sourceFile, (node) => {
        if (ts.isImportDeclaration(node)) {
          const importPath = (node.moduleSpecifier as ts.StringLiteral).text;
          if (importPath.startsWith("@db/") || importPath.includes("/orm/")) {
            const { line, character } = sourceFile.getLineAndCharacterOfPosition(node.getStart());
            violations.push({
              code: "LAYER-VIOLATION",
              file: filePath,
              line: line + 1,
              column: character + 1,
              message: `UI component directly imports database layer: "${importPath}"`,
              fix: "Route data access through domain service or repository abstraction",
            });
          }
        }
      });
    }

    return violations;
  },
});
```

### 2. Empirical Proof via Red/Green Fixtures
A rule cannot be added or updated based on good intentions alone. Every invariant rule must include:
- `should_pass/`: Positive fixture cases proving zero false positives.
- `should_fail/`: Negative fixture cases with inline annotations (`// expect: CODE`) proving the rule accurately detects violations.

```swift
// should_fail/swift/case1.swift
// expect: RAW-ENDPOINT-STRING
let data = await apiClient.request("/api/v1/users/export")

// should_pass/swift/case1.swift
let data = await apiClient.request(APIEndpoint.Users.export)
```

The engine verifies all fixtures before allowing a rule to be locked into the registry.

### 3. Cryptographically Signed Registry (`registry.lock`)
All active rules are tracked in `invariants/registry.lock`, formatted in deterministic Canonical JSON:
- `version`: Monotonically increasing version counter.
- `default_branch`: The cryptographically protected trunk branch (`main`, `develop`, etc.).
- `rules`: Mapping of rule IDs to their SHA-256 directory tree fingerprints.
- `signers_hash`: SHA-256 hash of `invariants/allowed_signers`.

### 4. In-Repo Team Governance & Ancestry Authority Chain
- `invariants/allowed_signers` lives directly in Git, tracking authorized team SSH public keys.
- **Ancestry Authority Chain (`checkSignerAncestry`)**: When an update is committed, `invariants` inspects Git history back to the parent commit. Only keys that were already authorized in the parent commit can approve updates to `registry.lock` or `allowed_signers`. An agent cannot self-authorize a rogue key.

### 5. Protected Trunk Branch Defense (`checkNoRewrite`)
Because `default_branch` is inside the signed `registry.lock`, the engine enforces fast-forward trunk integrity during `pre-push`:
- Detects and rejects `git push --force` non-fast-forward rewrites on the trunk branch.
- Detects and rejects trunk branch deletions (`git push origin :main`).
- Permits unrestricted feature branch development.

### 6. Non-Intrusive Workflow
`invariants init` does **not** hijack your existing `.githooks/` directory or mutate `core.hooksPath`. You simply call `invariants check` inside your existing pre-commit hook, pre-push script, or CI workflow.

## Threat Model: How Invariants Defends Against Agent Hijacking

| Attack Vector | How the Agent Attacks | Defense Mechanism | Outcome |
| :--- | :--- | :--- | :--- |
| **Rule Modification** | Modifies `rule.swift` to disable an invariant check. | `FingerprintEngine` computes the rule's SHA-256 tree hash and compares it against `registry.lock`. | ❌ **Rejected** (Fingerprint drift) |
| **Registry Tampering** | Edits `registry.lock` to weaken rules or change `default_branch`. | Native OpenSSH signature verification (`ssh-keygen -Y verify`) fails because canonical JSON hash changed. | ❌ **Rejected** (`signatureInvalid`) |
| **Key Injection** | Generates a rogue SSH key and adds it to `allowed_signers`. | `signers_hash` in `registry.lock` breaks immediately without re-signing. | ❌ **Rejected** (`signatureInvalid`) |
| **Rogue Authorization** | Signs a weakened registry using its own newly generated key. | `FloorGuard.checkSignerAncestry` walks Git history and confirms the key was absent in the parent commit's `allowed_signers`. | ❌ **Rejected** (`unauthorizedSigner`) |
| **Trunk Force Push** | Attempts `git push --force` to rewind trunk history before an invariant existed. | `FloorGuard.checkNoRewrite` evaluates `git merge-base --is-ancestor` on `default_branch`. | ❌ **Rejected** (`nonFastForwardPush`) |
| **Trunk Deletion** | Attempts `git push origin :main` to delete the trunk branch. | `FloorGuard.checkNoRewrite` detects zero SHA `000000...` on the protected ref. | ❌ **Rejected** (`branchDeletion`) |
| **Version Downgrade** | Reverts Git working tree to an older registry version ($v1 < v5$). | Git DAG commit ancestry walking (`FloorGuard.checkHistory`) asserts $v_{\text{current}} \ge v_{\text{max}}$. | ❌ **Rejected** (`versionBelowHistory`) |
| **Local Hook Bypass** | Executes `git commit --no-verify` or `git push --no-verify`. | The ultimate floor is CI: running `invariants check` in GitHub Actions blocks the merge. | ❌ **Blocked at CI Gate** |

## Command Reference

### Initialize Invariants
```bash
# Initialize invariants/allowed_signers, registry.lock, and sign v1 with Touch ID
invariants init

# Specify custom trunk branch
invariants init --branch main
```

### Authoring Rules with Full IDE Autocompletion
Rules live in standalone files. To get syntax highlighting, jump-to-definition, and autocomplete for `InvariantKit` in Xcode or VS Code:
```bash
invariants dev
```
This generates a disposable `invariants/.dev/` workspace (automatically ignored by Git) linking directly to `InvariantKit`.

### Adding & Updating Rules
```bash
# Create a new rule scaffold with manifest and fixture templates
invariants new forbid-force-cast --target swift

# Test fixtures locally
invariants test forbid-force-cast

# Lock and sign the rule into registry.lock (prompts for Touch ID)
invariants add forbid-force-cast

# Update an existing rule after modifying fixtures (prompts for Touch ID)
invariants update forbid-force-cast
```

### Checking Invariants
```bash
# Run pre-commit check on staged files
invariants check --stage pre-commit

# Run full project verification (used in pre-push or CI)
invariants check --stage pre-push
```

### Managing Local Keys
```bash
# Generate dedicated Touch ID signing key in the Apple Secure Enclave
invariants key generate

# Print your public key to share with repository leads
invariants key show

# Check local hardware key status and enrollment in current repository
invariants key status

# Safely delete local private key from this machine
invariants key delete

# Reset and generate a fresh Secure Enclave key
invariants key reset

# Clean up old rotation backup files (.bak-*) from ~/.ssh/
invariants key clean
```

### Team Governance & Repository Signers
```bash
# List all authorized team signers in the current repository
invariants signers list

# Authorize a new teammate's public key (prompts for Touch ID to seal registry)
invariants signers add alice@company.com "sk-ssh-ed25519@openssh.com AAAAGn..."

# Revoke a departed or compromised key
invariants signers revoke alice@company.com

# Voluntarily rotate your local key with a 24-hour sunset window for the old key
invariants signers rotate
```

### Inspecting Repository Status
```bash
invariants status
```
Displays installed engine version, signature validity, Git floor, configured Git hooks, and the status of all active and draft rules.

## Open Standards: Zero Proprietary Lock-in

Trust resides in native OpenSSH cryptographic standards, not opaque proprietary formats. You can inspect, verify, and sign registries by hand using standard Unix tools:

```bash
# Verify signature manually using OpenSSH
ssh-keygen -Y verify \
  -f invariants/allowed_signers \
  -I "*" \
  -n invariants \
  -s invariants/registry.lock.sig < invariants/registry.lock

# Sign registry manually using your Touch ID key
ssh-keygen -Y sign \
  -f ~/.ssh/invariants_ed25519 \
  -n invariants \
  invariants/registry.lock
```
